# Delivery and ownership

Resolve the actual environment rather than importing another host's directory
layout or deployment process. This package supplies a method, not an installer.

## Distinct planes

| Plane | Question and evidence |
| --- | --- |
| Semantic source | Which maintained text owns this meaning? Read that source and its ownership rules. |
| Package or projection | Which resources and transformations reach the target? Inspect package closure and generator inputs. |
| Discovery and enablement | How does this consumer find and select it? Inspect its current catalog or declared discovery configuration. |
| Installed runtime | Which exact entrypoint and resources can the consumer retrieve? Read them through the consumer's actual route. |
| Invocation and behavior | Was it selected, applied, and effective in the relevant task? Inspect attributable task evidence. |

A source, archive, example, or test copy is active only when a current consumer
is configured or instructed to discover it and can read it. A matching name,
repository presence, or enabled import does not establish installation on
another host. Resolve project-local and shared scope independently. Native
settings and permission owners retain their authority.

## Package and publish

Identify the source owner and intended consumers before editing. For imported
material, preserve rights and attribution; place semantic adaptations in an
explicit maintained derivative or overlay rather than presenting changed text
as an untouched upstream copy.

Keep discovery metadata specific to the capability and situations it serves.
Make the entrypoint a useful router, and include resources required for the
selected method. Resolve local references within the complete package. For a
dependency outside it, verify that the consumer can discover and access that
dependency, provide a self-contained alternative, or state the access boundary.
Do not infer a sibling Skill's availability from its mention in a source.

Use the existing publisher, installer, or host-supported interface. Inspect its
current contract and read back the persisted target; avoid inventing a second
updater or mirror. Publication to different consumers may require distinct
packages when their role, tools, or scope actually differs. Advisory and
execution roles do not become identical because their files share a name.

For a rename, merge, migration, or retirement, inventory affected discovery,
references, manifests, generated targets, wrappers, and runtime copies. Establish
and read back the successor, update consumers through the owning interfaces,
then retire obsolete active routes. Preserve inert archives when they serve
recovery. Avoid two active semantic owners for the same capability.

## Readback and recovery

Verify the intended consumer's discovery, entrypoint retrieval, supporting
resource retrieval, and relevant tool prerequisites. A source hash or successful
archive build supports those limited claims, not runtime availability. When
host access is unavailable, report the exact unverified plane and keep source
or package readiness separate from an installation claim.

Bind recovery to the actual changed source and deployment route. Preserve the
prior working state where recovery cost warrants it; use the existing history
or publisher rather than creating another version store. Read back an uncertain
mutation before retrying, so a transport error does not cause duplicate work.
