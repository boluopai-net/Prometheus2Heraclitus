# 工具使用

一份实践指南：从用上一个模型订阅开始，完成一件实际任务，逐步改进自己的工具与工作环境。用母语阅读和理解，把调查、实现和维护交给模型，通过实际使用继续修改。这里选择 Mac 与 ChatGPT / Codex 作为一条具体路线；你已有的其他电脑和实际可用的模型工具，也可以承担这些工作。

**具身全模态学习、具身全模态理解、具身全模态工作，把它们投入你的生活。**通过文字、图像、声音、身体经验与实际行动形成理解，把想法变成作品，再让世界的回应修正判断。“全模态”是在任务需要时调动可用的感知与表达，不要求每件事都塞进所有媒介。模型与环境承担细节和重复劳动，你通过阅读、观看、倾听、表达与实践，培养整体感、直觉、判断与创造。

## 1. 设备与网络：先让现有电脑能工作

如果你已有一台能运行所选工具的电脑，先用它。选择 Mac 时，核对软件当前的系统与芯片要求；内存、存储和外接屏幕按实际项目与使用负担再添。通过云端模型开始这条路线，不需要先购买用来本地训练大模型的显卡，也不必先把桌面布置成作者的样子。

网络应当能支持登录、查文档、下载依赖和上传作品。需要代理配置时，[Clash Verge Rev 的项目仓库](https://github.com/clash-verge-rev/clash-verge-rev)是可核对的客户端入口：它管理网络配置，本身不提供网络服务或模型账号，仍需你自己可用、可信的配置。[DuyaoSS](https://www.duyaoss.com/)可作为查找机场介绍、测速记录和线路科普的社区参考；页面可见的部分测速与介绍样本较早（2018—2024 年），优惠信息也注明可能未及时更新。把它当作线索，购买或配置前核对服务商当前条款与线路，并按自己的运营商、地区和设备实测；单篇测评不保证你当前网络的表现。安装一个客户端，不等于已经连通服务。

对主要在中国大陆生活的读者，还要分别检查**网络连通**和**服务支持范围**。中国大陆不在 OpenAI 的 [ChatGPT 支持地区清单](https://help.openai.com/en/articles/7947663-chatgpt-supported-countries)中；代理客户端不会改变这项服务条件。先确认你实际可用的服务与账号，再选工具；这份实践方式也可以用其他实际可用的模型来展开。

代理流量有限，或者大型软件、依赖包和 Docker 镜像下载缓慢时，可以让模型检查合适的**镜像源与缓存**。软件包源和 Docker 镜像仓库是不同的配置对象；镜像能够直连时，可以减少代理流量，缓存则减少重复下载。[Docker 的镜像缓存说明](https://docs.docker.com/docker-hub/image-library/mirror/)给出了按需从上游取得、随后从缓存复用的方式。让模型核对来源、支持的包或仓库、同步情况、版本及校验信息，再按当前网络实测；已有可用缓存时，不必反复清空重下。

## 2. 从订阅到全局提示词与关键 Skills

网页 ChatGPT 是云端的对话与工具空间，可以帮助讨论、研究、理解材料和发展构想。本地 Codex 则能在获得相应访问能力后，直接参与构建和维护你的**个人知识环境与工作环境**：连接资料、笔记、应用、文件、脚本、工具与配置，把想法做成实际可用的安排。一个项目文件夹只是其中一个工作位置，环境本身也可以是持续改造的对象。你带来目的、经验和判断，模型承担解释、调查、构造、执行与检查；从一个具体需要开始，就能让这种协作发生。

如果还没有可用账号，可以先解决网络连通，再选择并购买实际可用的订阅。先在 Web 中用起来，请模型帮助梳理目的与全局提示词；然后按 [官方入门说明](https://learn.chatgpt.com/docs/quickstart)下载本地客户端、登录，接入工作目录。已经有可用客户端时，也可以由它协助完成后面的准备。

先看现有账号是否已经包含所需 Codex 能力、额度和客户端。官方文档说明 [Codex 包含在 ChatGPT 方案中](https://learn.chatgpt.com/docs/pricing)，具体能力与额度随方案、账号和开放情况而异；可按 [登录说明](https://learn.chatgpt.com/docs/auth)使用 ChatGPT 账号。已有适用权益时，不必另买一份所谓“Codex 订阅”。遇到实际额度或功能不足，再比较升级是否值得。

### 先选稳定的个人订阅，再比较使用价值

**优先购买面向个人的 ToC 订阅，并把稳定性放在优惠价格之前。**先确认账号归属、持续登录、实际可用的模型与额度、续费和恢复方式；优先选择官方直购或来源清楚、交付与续费可靠的渠道。短期折扣不能抵消频繁失效、账号被收回或无法续用的代价。只有确实需要多人协作、组织管理、企业数据政策或合同保障时，再比较 ToB 团队／企业方案；不因“企业版”名称就默认它更适合个人。

**日常协作尽量围绕一个稳定的主订阅展开，让本地 CLI／App 与 Web 共同使用其实际包含的权益。**先把已有环境用顺，再根据实际能力差异决定是否增加或更换订阅。频繁切换会带来提示词、Skills、工具接口和操作习惯的适配成本；续费前仍应重新评估，稳定使用不等于永久绑定。翻译等有明确用途的接口仍可单独配置。

在稳定性和实际能力满足需要的候选中，**把本地与 Web 合起来看，并参考对应模型的 API 价格比较订阅价值**：

1. **列出真正用得上的能力。**分别核对本地和 Web 可选的模型、模式、工具、用量限制与重置周期；共用的额度只算一次，不能把两个入口当成两份额度。
2. **估计同类工作改走 API 的成本。**对有可比 API 的模型，按预计的输入、缓存输入、输出及必要工具用量，结合服务商当前价目表估算一个月的替代成本。例如可从 [OpenAI API 定价](https://developers.openai.com/api/docs/pricing)核对计费项。用不到的高价模型不增加实际价值；Web 专有能力或无法可靠估计的用量单独比较，不虚构精确折算。
3. **比较实际月费与能持续完成的工作。**结合本地加 Web 的真实需求、质量、速度、额度和续费成本，选择稳定候选中更合算的一项。API 替代成本是比较参照，不是把订阅月费除以 token 单价来推算“赠送额度”，也不是 API 单价越高就越值得买。

[ChatGPT 与 API 分开计费](https://help.openai.com/en/articles/9039756-managing-billing-for-chatgpt-and-the-api-platform)。订阅不等于 API 余额，API 余额也不替代订阅。只有你要做自己的 API 程序或确实选择 API 登录时，才需要另行了解这条计费路线。价格与支持情况请看官方当前页面，不在这里固定一个购买清单。

### 经常使用 Google 工具时，建议考虑 Gemini Pro

**如果准备把 Google Drive、Gmail 和 Gemini Notebook 作为日常资料、邮件与学习环境，建议考虑 Gemini Pro。**它可以作为主协作订阅之外的一项配套投入：购买理由不仅是多一个聊天模型，还包括把云盘、邮件和基于资料的学习工具用得更方便。

按 [Google 当前的套餐说明](https://one.google.com/about/google-ai-plans/)，可以把这些权益合起来判断：

- **云盘与邮箱容量：**扩展 Google Drive、Gmail 和 Google Photos 共用的存储空间，便于持续保存资料、文档和邮件。
- **Google 应用内的 AI：**在 Gmail、Docs 等支持的应用中使用 Gemini，辅助处理邮件和文档，减少在不同窗口之间搬运内容。
- **笔记与资料研究：**获得 Gemini Notebook 更高的使用额度，用于围绕已有来源提问、整理材料和生成音频概览等学习内容。

Drive、Gmail 和笔记工具本身已有免费功能；订阅增加的是容量、额度和相应 AI 权益。购买前用准备长期使用的 Google 账号核对[方案权益](https://support.google.com/googleone/answer/14534406?hl=zh-Hans)、所在地区与语言支持，以及实际续费价格。若只是轻量使用且免费额度够用，可以暂不加购；若本来就需要云盘扩容，又会经常处理邮件和研究资料，这种组合订阅更值得一起比较。

### 让模型帮助准备工作方式

全局提示词先写少量真正贯穿工作的安排：你希望怎样参与，哪些工作由模型承担，怎样使用母语与英文，文件和结果保存在哪里，以及模型怎样把事情完成并让你看见。可以先让 Web 模型帮助成文，再由本地模型放到客户端实际读取的位置，检查它是否生效。你提供目的和修正，不必自己维护一整套指令文件；提示词也会随使用而修改。

**作者建议：日常工作采用简单、全局共享的 Skills、插件与 MCP 配置，并把 Full Access 作为本地全局工作的默认模式。**让同一套有用能力能够随任务调用，只有具体项目确实需要不同设置时，才保留局部例外。这里的判断是：不必要的限制可能把工作引向绕行、反复中断，或为了维持 agent 运行框架而牺牲原本的用户目的。应让框架服务于实际工作，再根据具体问题修订，而不是为每项任务另造一套限制配置。

这是本指南选择的工作方式。Full Access 移除本地沙箱与通常的逐次审批提示；产品对具体工具与应用操作的控制、操作系统身份验证，以及服务账号授予的访问能力仍按各自实际机制生效。它让模型更连贯地执行已有范围内的工作，不会让云端连接、本地登录或服务权限凭空出现。具体含义可对照[权限说明](https://learn.chatgpt.com/docs/permissions)与[审批和安全说明](https://learn.chatgpt.com/docs/agent-approvals-security)。

接着让模型从可信来源选择、下载并验证眼前需要的 Skills。起步时可覆盖搜索研究、本地环境诊断、脚本与工具制作、文档阅读、界面实现、版本保存与发布；选择已有客户端能够使用的包，检查来源、兼容性和实际调用，不必先装满一个技能商店。关于这类能力包，可从 [Agent Skills](https://agentskills.io/home)了解其形式。全局共享指在支持它的客户端中统一维护可复用能力；不同工作现场实际能用什么，还要看[接通的环境](#continuity)。

需要图形化管理多个客户端时，可以选用 [CC Switch](https://github.com/farion1231/cc-switch)，管理提供商配置，以及它支持的 MCP、Skills 和 Prompts。它是可选的客户端配置管理工具；配置变更后，仍让模型从实际使用的客户端回读，确认选定提供商、指令和工具确实生效。已有简单、可维护的配置足够时，就继续使用它。

### 从实际任务形成适合自己的设置

先告诉模型眼前要做什么、已有材料在哪里，以及你在语言、解释方式、分工和结果呈现上的偏好。例如：“和我用中文讨论，帮我把这份材料整理成容易阅读的版本，保留来源，并实际检查链接。”这些工作背景和偏好可以随任务逐步补充，由模型维护到合适的提示词或项目说明中，你通过使用和纠正检查它们是否贴合。

**日常在聊天里写提示词，尽量用清晰、完整的自然语言，避免用比喻代替具体说明。**把想完成的事情、相关背景和重要要求说清楚；例如“请把这份报告改得更容易理解，解释关键术语，保留论据和来源”，比“给报告注入灵魂”更容易让模型判断该做什么。比喻容易留下多种解释，使模型难以准确遵循。你不必一次写成完整规格；模型可以帮助展开尚未说清的部分，再通过实际结果继续修正。

**阴阳中的六份实际文件与 `personal` 中的个人信息，也需要清晰的形式，不能只用哲学或文学来写。**私人的 `references/situated/` 中，六份实际文件是人与模型协作的工作模型，分别说明方向、个人、伙伴、关系、环境与实际修订方法，选取让实际个人环境在心理与实际使用上适合这个人所需的含义。心理与生活证据及持续维护的解释，主要保存在 `references/personal/`，相关原件留在既有维护位置，通过其中的来源索引取得。公开的写作指南说明怎样形成这些描述，具体个人的实际描述仍保留在私人环境。写清所描述的对象、概念之间的关系、陈述的根据与适用条件，区分实际信息、解释、所选择的方向和仍不确定的部分，让模型能够理解、推演，并据此参与实际工作。日常给模型读取的文本，优先用明确的提示词与背景说明来表达；直接说明仍不能说清重要关系时，再借助哲学或文学，并写明它在这里的具体含义。形式不要求统一模板或符号表示，个人信息也不因模型读取就成为命令。

**网页中给人阅读的哲学文章及其源稿，可以用哲学与文学充分展开思想，让整体目的和关系可理解、可感受。**模型同时修筑这两种彼此对应的表达：一边让人理解、判断和修正生活中的安排，另一边让模型通过明确的描述、提示词、工具与配置实际构建和维护环境。同一份理解在两边取得不同形式，实际使用的结果又能修正两边；既不把哲学文章改成操作手册，也不让模型只能从意象中猜测该怎样工作。

写出一套个人哲学是困难的长期工作。工具起步先完成一件真实任务，再改进环境；不把哲学写作、完整个人画像、六份实际文件或个人网站列为准备步骤。对思想背景有兴趣时，可以按问题选读 [Yinyang 的方法与资料](https://boluopai.net/repositories/prometheus/)；这些阅读与眼前的工具配置各有用途。

### 让 Skills 用中文被发现和组合

**建议在每个 Skill 的 `description` 开头写简短的中文名称和用途，同时保留准确的原生英文标识符。**这样你可以只用普通中文表达目的，让模型从当前可用的能力中发现、选择、读取并调用合适的方法，不必记住技术英文名称。中文说明帮助理解和发现，原生标识符仍用于准确安装、调用和更新。

区分来源时，用户自制的描述以 `<用户自制>` 标记开头，随后用空格接中文名称和用途。例如：「`<用户自制> 资料整理：整理选定材料并保留来源。`」这样来源标记与「名称：说明」分开。外部描述可以是「PDF 阅读：读取和检查 PDF 文档。」；翻译或本地改装外部 Skill，不会自动改变其作者来源。让模型在维护源、描述校验与客户端发现列表中一起核对，避免更新后恢复旧格式。标记用于辨认来源，原生英文标识符仍负责准确调用。

**选择上优先考虑贴合自身目的的自制方法，并把相关方法作为能够配合的工作能力主动组合。**它们可以贯穿理解需要、配置环境、开展任务与修订结果；外部专门方法则按实际贡献一起使用。优先级来自任务、适用范围与方法是否合用。

接下来就用已有能力完成一项实际工作：需要时搜索和接入工具，只有缺少合适实现时再编写。自己的工作方式由目的、使用与反馈逐步形成。

### 知道自己现在能用什么

**保留一份人能读懂的能力地图，而不只留下模型能找到的配置。**写清每类能力能做什么、从哪里开始、结果放在哪里、哪些环节已经接通。工具名称和脚本路径可以留作后面的入口；前面先用日常任务唤起印象，例如「找论文并取得可读全文」「把概念做成可操作的图」「修改表格并核对结果」。工具更新时，让模型同时修改这份介绍。已有工具被忘记，也是使用上的缺口。

| 想做什么 | 可以从哪里开始 |
| --- | --- |
| 找资料、找回以前的工作 | 搜索研究、论文检索、已连接文档，以及相关 History 和项目版本；模型沿线索回到原文和当前状态。 |
| 读书、学习或推进研究 | 老师方法负责讲解与接续，学科与研究方法库提供专业参考；专用安排见[科研与学习](https://boluopai.net/research-learning/)。 |
| 制作或修改成果 | 文档、表格、演示、网页、图示、图像与音频能力；从实际需要的文件或作品出发，交付能够检查的结果。 |
| 调整或修复自己的环境 | 环境设计、应用配置、浏览器与设备操作、诊断和版本维护；模型把修改接回原来的使用入口。 |

能力多时，还可以提供一个读取实际状态的 Skills 面板。可以让模型准备一个本地开关页：按全局或具体项目查看已安装能力，辨认插件、单项 Skill 的启用状态，以及是否允许模型主动选用。研究项目中的专用包不必全部放进每次聊天；选择当前项目，就能把相关能力带进工作。开关页负责查看与调整，中文菜单负责方便调用，介绍页负责让人理解用途，它们各有作用。保存开关后，以新任务中的实际发现和调用为准，已有对话中的旧内容不会因此被擦除。

<a id="reading"></a>

## 3. 翻译与母语阅读

先把需要的外语材料翻译成自己的母语，再用母语阅读和理解，把注意力用在内容和关系上。对以中文为母语、也习惯中文阅读的人，说明、导航、比较、进度和结果优先用中文；其他读者按自己的母语与实际习惯选择。在关键词、论证分歧或译文不通顺处，再对照外语原文。理解一个问题不必先变成一次英语考试；想练英语时，再主动切换阅读方式。

- **长网页：**把可用的翻译 API 接入[沉浸式翻译](https://immersivetranslate.com/zh-Hans/docs/services/openai/)或 [Read Frog](https://www.readfrog.app/en/docs/providers/overview)，保留双语对照。读正文时减少来回切换，原文仍在旁边供检查。
- **选中文字、图片和软件界面：**Mac 上的 [Bob](https://bobtranslate.com/guide/quickstart/translate.html)支持划词翻译、截图翻译和把译文放回图片上的原图翻译。能选取文字时直接取词，不能选取时再截图；识别与翻译使用的服务分别决定结果。
- **较长的文档和课程：**请模型整理可接续的阅读版本，保留标题、公式、图表、代码与来源。翻译帮助理解，重要定义与推论仍要能回到原文；公式和代码不能为了中文化而被改坏。

### 翻译界面与翻译 API 分开选择

Bob、沉浸式翻译和 Read Frog 是阅读入口，实际翻译可以来自另一项服务。**翻译可以先用免费 AI。**例如 [AIHubMix](https://aihubmix.com/models/free)、[OpenRouter](https://openrouter.ai/collections/free-models/) 和 [NVIDIA API Catalog](https://docs.api.nvidia.com/nim/docs/product)都有可考察的免费模型或试用入口。直接告诉模型：“帮我选择一个当前可用的免费翻译接口，接到我使用的翻译工具里，并实际译一段。”服务的开通条件、可用模型与接入细节，让模型按当前情况核对和配置即可。

少量取词和段落翻译通常适合先试免费方案；**整页、连续多页或大量文档翻译**会发出更多请求，更容易遇到限流、等待或额度不足。可以让模型减少并发、保留已有译文，或在需要持续大量阅读时比较低价付费接口与已有订阅的可用能力。[OpenRouter 的限额说明](https://openrouter.ai/docs/api_reference/limits)和各服务的当前页面用于配置时核对，不需要先记住一张免费额度表。翻译界面是否收费，与它调用的模型是否免费，是两件事。

另一条路线是把已有模型订阅经由自己管理的网关或代理转成兼容 API，再供翻译工具调用。[Sub2API](https://github.com/Wei-Shaw/sub2api)提供订阅额度接入、上游路由与客户端密钥管理；[CLIProxyAPI（CPA）](https://github.com/router-for-me/CLIProxyAPI)提供 OpenAI、Gemini 与 Claude 兼容接口，并支持 Codex OAuth 等上游接入。按已有账号与翻译工具实际支持的协议选择合适实现，无需同时安装两套。这里的作用是把已有上游能力接到 Bob 的适用插件、沉浸式翻译或 Read Frog 等入口，仍消耗对应订阅或服务的额度，不会新增官方 API 余额。前面的 CC Switch 管理客户端配置，这里的网关承担请求接入与转接；用途相连，作用不同。按上游条款与账号实际条件选择，连通本身不构成官方支持保证。

配置时，让模型对齐**接口地址、认证密钥、模型名称和协议**：扩展支持 OpenAI 兼容接口时使用对应设置；Bob 则选择适配该接口的服务或插件。先翻译一段文字，再检查长网页的分段、速度和额度，以及截图的文字识别。密钥由密码管理器或应用的凭据位置保管，公开配置只留占位和说明。

例如，可以用 [Bitwarden CLI](https://bitwarden.com/help/cli/) 管理密码、API key 和访问令牌：把凭据保存在保险库里，工具在需要时通过命令行读取对应条目。让模型配置和验证这条读取路径，公开文件只留下条目引用、占位和使用说明，真实值不进入聊天、日志或 Git。访问保险库数据需要有效的登录与解锁会话；这部分也应按实际环境安排。

人的阅读语言与模型的工作语言可以分开。本指南采用这样的安排：**给人看的用母语；主要供模型维护的技术说明、任务交接和工具指令默认用英文。**英文资料、术语和接口生态使这种安排方便；具体模型在具体任务上是否更有效，还要看实际结果，不能推成“所有模型用英文都更强”。原始材料、引文、代码、路径和接口字段保持其所需语言与格式。最终解释不能因为实现材料是英文，就把翻译负担退回给人。

可以直接告诉模型：“和我用中文讨论，把我需要判断的结果、依据和选择用中文讲清楚。供模型接续的技术材料默认用英文；原文、代码和标识符保留准确形式。需要我理解的英文段落，请就地解释。”翻译服务可能把选中的文字或截图发送到配置的服务商，私人材料按其实际数据去向选择处理方式。

## 4. 扩大信息来源，也保留判断

在这条实践路线里，**Telegram 主要用来寻找订阅购买渠道，以及其他服务、商品和零散资源**，也可用于联系卖家、比较方案与处理售后。[频道与群组](https://telegram.org/faq_channels)是信息和联系入口，实际交易由具体提供者承担。购买时辨认官方订阅、第三方代购和共享方案的区别，核对交付内容、有效期、续费方式与账号归属。渠道选择同样先看长期可用与售后，不为低价牺牲主订阅的稳定性，也不把群组人数或卖家宣传当作可靠性的证明。它也能补充日常信息来源，但这里不把它当作论文或专业资料采集的主要工具。

### 查最佳实践，也检查文档的时效性

了解工具当前实际怎样工作时，**优先查近期、注明版本并有可复现步骤的社区 Issue、PR 与使用反馈**。核对日期、客户端版本、平台和相关账号条件，再看问题是否已修复、建议是否仍适用。官方文档也可能滞后；具体接口、配置、API 与服务支持范围仍应查当前官方入口。遇到两边说法不一致，让模型比较适用条件，并用实际环境中的一次操作核对，而不是只凭来源名称决定相信哪边。

| 需要了解什么 | 基本入口 |
| --- | --- |
| 社区实践与当前问题 | [Claude Code Best Practice](https://github.com/shanraisshan/claude-code-best-practice)整理 agents、commands、Skills、Hooks、MCP、插件、设置与工作流；结合 [Codex Issues](https://github.com/openai/codex/issues)和 [Claude Code Issues](https://github.com/anthropics/claude-code/issues)查看具体问题与后续处理。 |
| ChatGPT 与 Codex 的使用 | [ChatGPT／Codex 文档](https://learn.chatgpt.com/docs)与 [OpenAI 帮助中心](https://help.openai.com/en)。 |
| GPT 与 API 开发 | [OpenAI API 文档](https://developers.openai.com/api/docs)，用于核对接口与开发配置。 |
| Claude 的使用与开发 | [Claude 帮助中心](https://support.claude.com/en/)、[Claude Code 文档](https://code.claude.com/docs/en/overview)与 [Claude API 文档](https://platform.claude.com/docs/en/home)。 |

最佳实践仓库是可比较和借鉴的方法来源。让模型读出适合当前任务的部分，检查依赖、版本和实际效果，再决定采用或改装；不必整套安装，也不直接照抄其中的命令。社区报告同样可能过时或只适用于特定条件，保留能够回查的依据。

### 资源获取与非正版的条件判断

资源是否“正版”也需要拆开看。作者公开稿、开放获取论文、公共领域作品、开放许可材料和图书馆资源都有各自的获取与使用条件，免费并不等于盗版。先请模型寻找适合的版本，核对内容、来源和用途，而不是只找一个能下载的链接。关于授权、公共领域与例外的基本区别，可参考 [WIPO 的版权问答](https://www.wipo.int/en/web/copyright/faq-copyright)。

也可以把 **Anna's Archive** 和 **Sci-Hub** 纳入资源渠道的判断：前者聚合书籍与论文等记录，后者主要面向学术论文。这类站点涉及未授权副本与版权争议，具体材料仍按下面的条件区分。域名与可达性会变化；这里提供 [Anna's Archive 背景与入口信息](https://en.wikipedia.org/wiki/Anna%27s_Archive)和 [Sci-Hub 背景与入口信息](https://en.wikipedia.org/wiki/Sci-Hub)，使用时核对当前来源，不把搜索结果中的同名镜像都当成同一个站点。

对疑似未经授权传播的资源，可以把可获得性、经济条件、个人学习目的和对创作者的影响放在一起讨论。**这些条件可以进入伦理判断，却不能自动证明复制、传播或使用获得了许可。**阅读参考、复制保存、再分发和商业使用是不同的行为；依据具体资源的授权与适用规则分别判断，保留出处，不把取得一份副本当成继续传播的权利。软件还涉及可执行代码的来源与完整性：优先寻找可信的开源替代、试用或教育方案，不把来源不明的破解安装包当作普通阅读材料。

## 5. 自制工具，让环境适合人

**贯穿这些安排的目的，是控制复杂性。**你不需要照搬作者的电脑、目录或工具组合；判断一种安排有没有用，要看它是否减少理解、操作与维护的负担，同时保留你需要的能力。工具更多、分工更细，都不自动等于环境更好。

软件工程里的一条相关思想是**窄而简单的接口，承载深而丰富的功能**。John Ousterhout 的书[《软件设计的哲学》](https://web.stanford.edu/~ouster/cgi-bin/book.php)讨论了接口复杂度、功能与信息隐藏的关系。放到个人环境里，可以把“帮我准备这本书的阅读材料”作为人的入口，让模型在背后完成找版本、转换、组织与核对；人仍能看到来源、结果和需要自己判断的差异。这里的“窄”指必须掌握的操作与约定少，不是把自然语言意图或可处理的内容限制得很窄。复杂性被放到能够处理它的地方，重要选择仍然可见。

目标可以是把**整个日常工作环境的建设与维护托管给模型**：安装和配置软件，整理资料，写工具，修复故障，维护提示词和 Skills，再把这些改变接回日常使用。人主要表达目的、阅读、判断与反馈，只写必要的 Markdown；模型承担其余成文、代码、配置和持续维护。它需要有清楚的工作范围、可用工具和能接续的记录；购买、身份验证、公开发布等个人决定仍由实际授权来确定。

把人的入口和模型的入口分开设计。人需要母语标签、清楚的层级、可点击的标题、能看见的状态和结果；模型可能更适合命令行、结构化数据、明确的工具接口与维护说明。两种入口通向同一份工作，内容有可维护的源，不靠人来同步两份副本。能由模型确定的工具选择和重复步骤，就由模型接上；需要人的目的、判断和授权时，再把选择呈现出来。

### 先配搜索，优先使用已有工具

采用一种组合与改装现成工具的 Hack 式工作方式。先给模型配好实际可用的网页搜索、GitHub 搜索和文档读取能力，并用一次真实查询验证。遇到需求，先找网上是否已有合适实现，读项目说明、近期维护和使用反馈，再决定采用什么。模型接着安装配置，并按工具特点安排版本检查与更新；不合用的部分可通过设置、插件、小补丁或改写来适配环境。确实没有合适实现时，再自己写。更新也要检查它是否仍能完成原来的工作，并保留可恢复的版本。

可选的搜索工具有不少，可以按实际用途组合：

- **通用网页与资料发现：**[Brave Search](https://brave.com/search/api/)可以查网页、新闻等信息；[Parallel](https://parallel.ai/)、[Exa](https://exa.ai/)和 [Tavily](https://www.tavily.com/)提供适合模型调用的搜索与资料获取能力。让模型根据来源覆盖和实际结果选择，不必每个问题都调用所有服务。
- **页面读取与成批提取：**[Firecrawl](https://www.firecrawl.dev/)可用于读取网页、抓取站点和提取内容；先搜到对象，再深入读取原文。需要了解近期社区讨论时，也可以使用已接入的 Last30Days 多来源研究工具，按问题设置时间范围。
- **论文与学术资料：**[Consensus](https://consensus.app/)、[SciSpace](https://scispace.com/)和 [Hugging Face Papers](https://huggingface.co/papers)是可选入口，其中 Hugging Face Papers 更贴近 AI 论文生态。发现相关研究后，再回到论文、作者或出版方核对原文。

这些是具体例子，不是一份全部购买或安装的清单。已有客户端原生搜索足够时先使用它；覆盖、正文获取或专业资料不足时，再接入相应插件、MCP 或 API，并验证一次真实查询。多项工具返回同一来源，也不等于取得了多份独立证据。

### 在 Mac 上获取和管理应用

在 Mac 上，可以优先用 [Homebrew](https://brew.sh/) 获取和更新它收录的应用；希望用图形界面操作时，推荐 [Applite](https://applite.app/)，用它浏览、下载、安装、更新和卸载 Homebrew 应用，不必逐条输入命令。已有 Homebrew 时，可让模型检查 Applite 使用的是哪一份安装，再接到现有管理方式。

[MacKed](https://macked.app/) 也可以作为查找 Mac 应用与下载资源的补充入口。它是包含破解资源的第三方站点，具体软件的来源、授权和可执行文件完整性仍需分别判断；上文的资源获取讨论同样适用。

### 怎样使用别人的 GitHub 仓库

把仓库链接交给模型，并说清楚希望它完成什么。让模型先读 README、安装说明、许可证和当前支持的平台，再选择入口：

- **直接使用：**项目提供应用安装包或 Releases 时，按系统与芯片选择合适版本；命令行工具也可能通过 Homebrew、pip 或 npm 安装。源代码 ZIP 不一定是可以直接运行的应用。[GitHub 的下载说明](https://docs.github.com/en/repositories/working-with-files/using-files/downloading-source-code-archives)区分了源码快照与带历史的克隆。
- **在本地运行或学习：**需要运行源码、查看实现或持续更新时，让模型 clone 仓库，按说明准备依赖、配置和示例，用一个实际输入验证结果；只下载 ZIP 通常不包含 Git 历史。
- **按自己的需要改装：**先判断配置、插件或小补丁是否足够；需要维护自己的远程版本时再 fork。让模型保留修改的理由、上游来源和可恢复版本，更新时比较自己的改动与上游变化，处理冲突后重新验证。
- **提问、协作与复用：**先查已有 Issue 与文档；遇到可复现问题，可以整理环境、步骤与结果，通过 Issue 反馈，通过 PR 提交改进。[GitHub 的协作说明](https://docs.github.com/en/get-started/exploring-projects-on-github/contributing-to-a-project)介绍了这条路径。需要时让模型用 GitHub CLI 或已连接的 GitHub 工具处理这些操作；实际发帖按你的授权执行。仓库也可以只作为论文、文档、Skill、模板或实现思路的来源，具体复制与改装范围按其许可证确定。

### 用脚本、Hook、Skill 与接口连接动作

一个设置、直接链接或短脚本够用，就不必立刻造一个系统；当方法需要重复使用、跨项目调用或交给其他人时，再选择合适的封装：

- **小脚本：**连接具体动作。例如把当前资料整理成可点击的阅读页，给常用操作做一个有中文名称的菜单，或把后台任务的完成与错误显示出来。人的界面可以是按钮、菜单或网页，执行细节由模型维护。
- **Hook（钩子）：**把动作接到明确事件上，例如提交代码前检查格式、提交后记录结果；如果客户端提供相应事件，也可以在工具执行后整理输出，或在任务完成时显示通知。[Git hooks](https://git-scm.com/docs/githooks)是这种机制的一个具体例子。Hook 的事件、输入和失败处理由实际宿主决定，不能把一个客户端的配置直接照搬到另一个。让模型接到已有入口，触发一次真实事件并读回结果，避免把“记得做某事”只留在提示词里。
- **Skill：**把一类工作的目的、方法、所需材料与检查方式写成模型可以按需读取的能力包。[Agent Skills](https://agentskills.io/home)可以带说明、脚本、参考资料与模板；有价值的是它能让下一次工作接续，文件多本身没有价值。
- **MCP：**当模型需要稳定调用一个数据源或操作时，用 [Model Context Protocol](https://modelcontextprotocol.io/docs/getting-started/intro)提供工具与资源接口。例如让模型查询资料目录、读取选定笔记，或调用已有的转换程序。配置所需的服务连接与读写能力。
- **插件：**当所用客户端支持时，把相关 Skill、工具连接和资源组织成便于安装、发现与更新的一组能力。具体包装由客户端决定；一个本地脚本并不必须先变成 MCP 或插件才能有用。

在 ChatGPT 与 Codex 的[统一插件目录](https://learn.chatgpt.com/docs/plugins)中，可以从 **Plugins** 安装所需能力，按需要连接对应服务，再在新对话中使用。安装让包可用，服务连接让当前账号能访问相应资料与操作；还要从实际对话确认所需工具是否已经提供。Google Drive 插件覆盖 Drive、Docs、Sheets 与 Slides；GitHub 连接可以提供仓库、Issue 与 PR 等工具，实际读取和写入范围由服务授权与当前接口决定。不能把「显示已连接」当作所需操作已经可用。

自制能力与这些原生连接可以一起工作：Skill 说明怎样处理一类工作，MCP 服务提供真实的数据与操作工具，插件把相关部分组织成可安装的能力。模型可以组合它们完成资料检索、文档修改或代码协作，并按当前客户端与工作现场实际提供的接口开展工作。让它用眼前任务需要的一次实际读取或修改核对结果。

自己的 Skills、脚本和接口则可以围绕真实工作逐步形成。网站的[可复用 Skill 目录](https://boluopai.net/skills/)还提供抽卡转盘、研究、教学、论文与字幕、练唱、安卓控制、购物、提示词审计和环境维护等方法。各页用一个中文名和原生英文名标识 Skill；包内说明需要哪些配套 Skill 与真实工具，按需一起下载，保留有用的分工关系。MCP 与连接器也可以很具体：[Jev MCP](https://github.com/jkudish/jev-mcp)提供文本判断工具，[Logic Pro MCP](https://github.com/MongLong0214/logic-pro-mcp)连接音乐软件并读回项目状态，[PhotoCraft](https://github.com/storytold/photocraft)提供图像编辑能力，[ChatGPT Sites](https://help.openai.com/en/articles/20001339-creating-and-using-chatgpt-sites)可创建、预览和发布网站。这些都是可选例子，按眼前任务挑选即可。

脚本还可以进入很具体的日常动作。在 Mac 上，让模型把选定的整理、检查或同步脚本做成 **LaunchAgent**，在登录后、定时或合适的触发条件下运行，并留下可以检查的结果。为常用动作设计**快捷键**，例如打开一组工作资料、翻译当前选文、开始或结束录音；检查按键冲突和当前应用，再让这些动作接入已有操作习惯。也可以使用 **AI 输入法**，把口述转成文字、补充标点、整理表达或进行中英混输，再按实际输入框核对结果。经常在中文句子里夹带英文产品名或技术术语时，可以优先试用中国厂商面向中英混合口述的输入法或转写模型，让这些词和中文一起被识别；用自己的说话方式比较转写准确度、标点与修改量，再选择顺手的一项。工具的作用是缩短想法到表达与行动的距离，配置与维护可以交给模型完成。

还可以围绕这些需要制作工具：把 PDF 整理成保留公式和来源的阅读材料；把取词翻译接在当前阅读动作上；把难记的命令做成可搜索菜单；把作品、原文与版本用直接链接连起来；让后台工作报告完成或失败，同时保留当前窗口、输入焦点与正在做的事。这些是按问题选择的例子，不是一份要求读者全部安装的清单。

### 生成图像、用图解释与编辑图像

让模型选择适合当前问题的视觉形式。**生图**可以用于插画、人物、氛围图和图像方案，把描述变成可供比较的画面；涉及精确数字、关系或文字时，要检查图像有没有改变原意。**用图解释**可以用 [Archify](https://github.com/tt-a1i/archify) 制作可浏览的架构、流程和状态图，用 [Diagram Design](https://github.com/cathrynlavery/diagram-design)组织概念、比较和关系图；解释变化与选择时，也可以做可交互的网页，让读者操作条件并看到结果。它们是各自上游维护的工具与方法，按其说明和许可使用。

**编辑已有图像**可以使用 [PhotoCraft](https://github.com/storytold/photocraft)，让模型打开指定图片、检查可用操作、完成编辑、预览并导出。生成新图、解释关系和编辑原图承担不同任务，模型应根据你要理解或制作什么来选。给学习材料配图时，把关键对象、箭头关系、条件与原文依据接在图旁，图像才真正参与理解，而不只是装饰。

### 用 Skill 与 Project 组织生活中的工作

这套方式可以进入生活中的许多领域：心理探索与经验整理、购物比较、课程学习、就医准备与医学资料阅读、工作项目、游戏配置与攻略、运动记录与计划，以及音乐欣赏、录音和练习。领域不同，需要的知识、证据和专业支持也不同；模型可以帮助选用和形成合适的方法，再接上实际可用的工具。

**Skill 保存可重复使用的方法，Project 组织一项持续的目的、材料与成果，工具完成具体操作。**例如，购物 Skill 可以用于不同购买任务，一个持续的学习 Project 则保留课程、进度与练习；音乐项目可以连接练唱方法、录音软件和历次作品。Project 可以是客户端里的项目，也可以是由本地文件夹、说明和版本组成的工作空间。让实际目的、已有理解和使用反馈提供共同方向，各领域的方法继续发展；简单问题可以直接处理，反复或长期的工作再积累成可接续的 Skill 与 Project。

### 阅读、终端与 Vim 式操作

- **浏览器：**[Vimium](https://github.com/philc/vimium) 这类扩展把 Vim 式操作带到网页：用 `j` / `k` 滚动，`f` 显示链接提示并打开链接，`/` 搜索页面，`H` / `L` 返回或前进，也能搜索与切换标签。让模型按实际浏览器选择扩展、配置常用键位和站点例外，并在阅读页、表单与常用网站检查效果。扩展支持的网页范围与输入框状态会影响按键，不能只按安装成功判断。
- **Obsidian：**让人读取和修改必要的 Markdown，模型维护关联材料、链接和结构。它提供[阅读与编辑视图](https://obsidian.md/help/edit-and-read)，编辑器可直接开启内置 [Vim 键位](https://obsidian.md/help/settings)，无需为了基本 Vim 编辑先装社区插件。阅读模式、标签切换和插件操作需要分别配置与检查；只有内置功能满足不了实际动作时，再让模型核对合适的插件及其当前兼容性。
- **IDE 与代码编辑器：**VS Code 可用 [VSCodeVim](https://github.com/VSCodeVim/Vim)，JetBrains IDE 可用 [IdeaVim](https://github.com/JetBrains/ideavim)，在现有编辑器中采用 Vim 的模式、移动与编辑习惯。代码补全、调试、项目导航和其他命令仍由 IDE 提供；让模型配置键位分工，并在实际项目检查编辑、补全和调试时的冲突，不必为统一操作替换整个 IDE。
- **Sioyek：**用来阅读教材与论文 PDF，保留原始版式，并用它的[导航、搜索和标记能力](https://github.com/ahrm/sioyek)往返材料。模型可以整理阅读入口、配置键位，并把引用连回具体文件。
- **cmux：**把终端与模型任务放进可辨认的工作区；它提供[垂直标签、分屏和可编程接口](https://cmux.com/)，便于看见多项工作的名称与状态。
- **终端中的编辑与命令行：**[Vim](https://www.vim.org/docs.php) / [Neovim](https://neovim.io/doc/user/) 用于编辑文件；shell 的 Vi 模式用于编辑尚未执行的命令，两者不是同一个入口。在 zsh 中可从[内置 `bindkey -v`](https://zsh.sourceforge.io/Doc/Release/Zsh-Line-Editor.html) 开始，确实需要更完整的命令行 Vim 操作时，再考虑 [zsh-vi-mode](https://github.com/jeffreytse/zsh-vi-mode) 插件。让模型检查当前 shell、已有补全和历史搜索，配置后实际试过输入、修改、执行和恢复；终端的标签、窗格与滚屏仍由终端应用分别管理。

让模型把跨应用的常用移动、搜索、返回、标签和窗格切换尽量统一成 Vim 式习惯。各应用的能力不同：编辑器的 Vim 模式、PDF 导航和终端工作区不是同一套功能，模型要在实际入口检查冲突与结果，而不是只交出一张快捷键表。鼠标入口、中文标签和可搜索菜单仍然保留，Vim 式操作服务于熟悉的动作与低切换成本。

### 编排 UI：垂直排列，把重要的东西放在前面

**多页面、多文档和多任务界面，优先使用实际可用的垂直标签栏、列表或侧栏。**把工作按目的分组，使用容易辨认的名称，让相关材料与任务相邻；重要、常用和当前正在推进的内容放在上方，支持时置顶。低频内容可以折叠或归档，别让默认的“最近更新”排序持续决定自己的注意力。

| 界面 | 可以怎样编排 |
| --- | --- |
| Codex | 用左侧垂直任务列表和项目分组组织工作；按当前版本可用的置顶、排序与归档功能，让重点任务容易找回。 |
| Chrome | 使用当前版本可用的垂直标签栏、侧栏或标签组，把同一目的的页面放在一起；常用入口放前面，暂时不用的组收起。 |
| Obsidian | 用侧栏[书签](https://obsidian.md/help/plugins/bookmarks)保存常用笔记、分组并调整顺序；用[工作区](https://obsidian.md/help/plugins/workspaces)保存某项任务的打开文件、标签与侧栏布局。 |
| cmux | 用[垂直标签栏](https://cmux.com/)辨认终端与模型任务，按工作目的组织工作区，让相关工作容易切换和找回。 |
| Web ChatGPT | 整理侧栏中的对话与 Projects，用清楚的项目名聚拢相关工作；按当前可用的置顶、排序或归档功能保持重点可见。 |

让模型按实际应用能够提供的功能配置；自己制作的网页和工具也采用这些安排。允许侧栏折叠和调整宽度，窄屏时收起，给正文留足空间。改好后用一次真实任务检查：能否认出重要内容、切换到相关材料，并返回原来的工作。界面的编排随使用调整，不必为了相似外观把所有应用改成同一套操作。

### 用 chezmoi 收拢全局配置

让模型建立一个由 Git 管理的全局配置仓库，使用 [chezmoi](https://www.chezmoi.io/what-does-chezmoi-do/)把分散的终端、编辑器、快捷键、脚本入口和可重建的模型配置收拢到可维护的源。模型修改源、检查差异、应用到实际环境，再从真实应用读回效果；GitHub 保存版本，便于继续维护、换机和恢复。收拢的是配置的维护关系，不是把所有应用数据塞进一个仓库；密码、令牌、登录会话、缓存和临时状态仍留在各自适合的位置。

Obsidian 的多个库也采用**一套共享基础配置**：主题、插件选择、通用设置和 Vim 键位统一维护，再由模型同步到各库，避免每个库手动配一遍。笔记内容保持在各自的库里；确有必要的库差异单独保留。云盘目录与普通本地目录的同步机制可能不同，由模型选择适合的复制或链接方式，并检查每个库实际加载后的结果。这样既精简管理，也避免一次共享配置更新误改笔记内容。

可以从一句话开始：“这件事我经常做，但现在要记住几个命令、来回开窗口。请检查现有做法，把它改成我看得懂的入口，保留结果位置、失败提示和恢复办法，并实际试一次。”请模型完成实现与验证。实际检查的是从人的入口能否完成工作、出了错能否继续；代码能够运行，只是其中一部分。

## 6. Web、Dot 与本地：让工作围绕共享资料接续

### 三种工作现场，接通同一份维护源

**这条实践路线以本地 Codex 为主要执行入口，让它持续构建个人知识环境与工作环境。**这种环境包括资料与笔记、阅读入口、应用设置、脚本与自动化、模型工具、工作偏好，以及不断产生的作品。模型可以按任务接通它们、改变其组织、检查实际效果，并维护之后仍要使用的安排。项目文件夹保存某项工作的材料；它不是整个人机协作的范围上限。

| 工作现场 | 工作所在的位置与可用材料 | 怎样参与持续工作 |
| --- | --- | --- |
| 网页 ChatGPT 的通用云端空间 | 对话、上传材料、已连接的云端资料，以及账号实际提供的搜索、研究、分析、生成和应用工具 | 讨论、研究、理解与创作，也可通过已接通的 Drive、GitHub 等工具处理其支持的资料和操作 |
| Dot 的云端工作与连接仓库的云端环境 | Dot 有自己的常驻云端电脑、浏览器与云端对话；编码任务还可使用已配置的 Codex 云端仓库环境 | 在持续云端工作中接续材料；仓库环境提供已发布的代码、依赖和工具，让任务能够运行、修改并交回结果 |
| 本地执行环境 | 实际可用的本机文件、命令、进程、应用接口与连接的服务 | 由本地 Codex 等入口调查并改造环境，整理资料，运行程序，检查结果并持续维护 |

三种现场说明**工作在哪里运行、模型接到了什么，以及结果在哪里持续存在**，不是权限高低的三个层级，也不是互不相通的产品分组。本地入口同样可以讨论与研究，云端入口也可以通过真实工具修改文档或处理 Issue、PR。Dot 还可通过桌面应用接通个人电脑，启动独立的本地 Work／Codex 任务；这时工作转到本地现场，需要电脑在线、应用保持打开。它的云端与本地会话、浏览器登录不会自动继承。具体关系可看 [Dot 的电脑与应用说明](https://learn.chatgpt.com/docs/dots/computers-and-apps)。

配置好的云端仓库环境是独立工作现场。[环境说明](https://learn.chatgpt.com/docs/environments/modes)区分本机与云端工作空间：云端任务使用已发布的仓库、依赖与工具，任务自己工作文件的变化不会自动更新可复用的环境。本地文件、进程、浏览器登录或 VPN 也不会因使用同一模型账号而自动转移。需要什么，就让模型接通当前现场的实际入口，并把必要变更保存回原有维护源。

本地客户端调用云端模型时仍需要网络；“本地”主要说明执行现场与可维护的材料、工具在这里。网页与本地也可能提供不同模型、模式和用量，按实际问题选择。需要网页模型的另一份判断时，让本地模型准备相关材料，再把有用结论接回环境中落实。人仍通过提出需要、理解结果和给出反馈参与，不必在两个入口之间反复复制背景和搬运实现细节。

### 文件、版本与公开表达

这里选择一套以海外服务为主的工作环境：模型订阅、GitHub、Google Drive、Telegram 与相关工具相互接通。具体采用哪些服务，以它们能否支持同一份工作为依据；账号、网络与数据存放位置需要在实际环境里能持续使用。

**Google Drive 放资料与日常文档，GitHub 放需要版本管理的代码、配置与 Skills，网页呈现适合阅读和参与的结果。**这些共享维护源让不同现场围绕同一份工作接续，减少资料只能留在某台电脑上的摩擦。通过 [Google Drive 桌面版](https://support.google.com/drive/answer/10838124?hl=zh-Hans)，选定资料可以在云端与本地之间接续；运行本地工具前，确认需要的文件已经下载可用。项目代码、Skills 与 chezmoi 配置仓库则由 Git 管理并推送到 GitHub。私人材料使用相应的私人空间；同步和版本管理按各自职责工作，不让多个机制同时争写同一份仓库状态。

共享来源与实际访问是两件相连的事。模型可以通过相应插件与服务账号，在当前现场读取或更新维护中的文档、仓库或协作记录；仍须确认具体工具和读写范围能完成任务。云端工作不是本地目录的自动镜像。让模型找到现有源、完成可用的操作，并把成果写回文档或仓库原有的维护位置；需要分支、提交或交接时，沿该项目的实际方式接续。这样不同入口交换的是有来源、可继续维护的成果，而不是不断手工搬运的副本。

先建立一个项目文件夹，让模型把第一版作品放进去。保留原始想法、正在维护的源文件和简短说明；以后你和模型回来时，能知道它做什么、怎样运行、还有什么问题。私人材料与准备公开的作品分开放，发布前看一遍实际将公开的文件。

[Git](https://git-scm.com/book/en/v2/Getting-Started-About-Version-Control)记录文件的修改历史。先会保存一次有意义的版本、查看变化和回到旧版本，就已经有用。[GitHub](https://docs.github.com/en/repositories/creating-and-managing-repositories/about-repositories)接上远程保存、讨论与协作；免费账号可以建立公开和私人仓库。Git 是本地版本工具，GitHub 是托管与协作服务，第一次做出作品时可以先只用本地文件。

想让别人直接读到或试到，再发布网页。[GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)可从仓库发布静态网页；GitHub Free 的这条路线使用公开仓库，适合你愿意公开的 HTML、CSS 和 JavaScript，不提供任意后台服务。可以先用它提供的网址，自定义域名以后再考虑。本网站使用 Sites；如果你的账号已有 [Sites](https://learn.chatgpt.com/docs/sites) 入口，也可以让模型准备、检查并发布网站，其可用性仍取决于方案、地区和工作区设置。

**Cloudflare 也是适合发布个人网站的选择。**[Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/)可以承载网页文件，并按需要接入后端逻辑；[Pages](https://developers.cloudflare.com/pages/)支持连接 Git 仓库或直接上传发布，Cloudflare 当前建议新项目优先考虑 Workers。让模型根据实际网站准备部署与自定义域名。个人网站也可以是仅供自己使用的工作台，这时应配置真实的登录与访问控制；“不被搜索引擎收录”不能替代私有访问。

实际工作现场承载正在发生的实践，GitHub 留下可检查的源内容，网页提供阅读与参与的入口。[哲学、心理与工程的三位一体](https://boluopai.net/philosophy/local-source-and-website/)进一步解释它们怎样属于同一份工作。

#### 把记忆外置，让历史能接续

**人约等于 agent，可以从有限的注意力和工作上下文来理解。**人和模型都需要把早先经历带入当前行动，却无法同时握住全部背景；这是一种功能类比，不意味着人的大脑采用大语言模型的架构。把有用记忆外置到文件、笔记或知识库，能让接续工作少依赖临场回忆，也让另一个模型有材料可读。

先让模型在已有项目里维护一份简短的当前说明：目的、已作出的选择、有效条件、未解决的问题，以及原始材料的位置。需要时用文件搜索、知识库检索或 RAG（检索增强生成）取回相关部分，再交给当前模型。外置记忆提供可查的背景，检索选择这次工作需要的材料；它们不会把全部经历瞬间传进一个上下文。例如，继续一份课程作品时，模型先读课程目标和上次未完成的部分，再按需要查原文。

**当前记忆与历史来源一起保留。**说明可以随着理解改变，来源记录则帮助检查“当时发生了什么、后来为什么改”。在提供且已启用 Computer History 的 Codex 环境里，它按观察设置保留滚动的活动事件流及摘要，可帮助找回近期用过的应用、页面与任务线索；覆盖范围取决于设置和实际捕获。Git/GitHub 的版本、提交与 PR 提供项目范围的历史，它们不是同一个 Computer History 产品，也不会自动记录全部电脑活动。可以把前者理解为跨应用的环境线索，把后者理解为项目内的变化线索，再回到原文件与当前状态核验。

把“较早的依据或行动 → 较晚的修改或结果”连起来，并在合适粒度上保持边沿发生次序向前，历史可以形成有向无环的来源图：原始需要 → 一个方案 → 一次提交 → 使用反馈 → 后续修订。[Git 的提交对象](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)也保留父提交关系。这里保留的是能解释变化的痕迹，不能据此宣称所有心理过程都是 DAG，或记录已覆盖整个人生。让模型沿相关痕迹恢复背景，再判断哪些记忆仍适用于眼前任务。[生活轨迹的形成](https://boluopai.net/philosophy/flow-and-time/)进一步解释这种保留与纠正。

## 7. 从模型的执行内环开始

你提出一个需要，模型完成调查、构造、执行、检查和修订；结果进入实际使用，你和模型再根据体验与后果调整需要。这可以理解为**内外两层嵌套的反馈环**：执行内环围绕当前任务反复检查与修复，使用外环则把结果放回人的生活，改变下一轮工作的方向。人可以只说几句话，让 AI 把这轮工作跑起来；不必亲自接管每一个步骤。

> 使用外环：表达目的与经验 → 看见并使用结果 → 共同判断、反馈与重新定向。
>
> 执行内环：模型理解任务 → 调查条件 → 构造与执行 → 检查结果 → 修订到可用。

这里的“内外”取决于选定的系统边界。执行内环也包含工具、实际运行和结果反馈，不只是模型内部思考。在控制工程中，[内环与外环](https://www.mathworks.com/help/control/ug/designing-cascade-control-system-with-pi-controllers.html)是常见的结构用语；这里借它说明人机协作的反馈层次，不把整套协作等同于一种特定的控制器。

第一个执行内环可以围绕一件实际需要的事展开：接通一项翻译服务、准备全局提示词、用起一个 Skill、整理可读的材料，或把常用操作改顺手。也可以制作课程页、研究问题、整理作品或建立仓库。事情未必小，但人的入口可以简单；模型负责把内部工作展开，直到结果能够实际使用。

1. **你给出目的，模型展开任务。**例如“让这篇英文材料能舒服地读”。模型查明材料、阅读入口与翻译条件，提出并实现合适的安排。
2. **模型把内部工作做到可用。**翻译服务要能译出真实段落，阅读入口要能找到原文；检查失败时继续修复。遇到必须由你提供的经验、授权或个人验证，再把那个具体问题带回来。
3. **模型保存可接续的成果。**必要的材料、配置与版本留在各自位置，使下一次工作有现成起点；你无需管理它的每个中间步骤。
4. **你使用和判断，模型继续修订。**你指出不方便、遗漏或理解错的地方，模型接着做下一轮。你的反馈也可以改变正在运行的工作方向。

沿着这些循环，工作偏好、环境、作品、GitHub 仓库、模型配置、Skills 和自制工具可以共同演进：目的引导配置，配置支持实践，实际后果又改变理解与实现。模型跟进一项改变真正影响到的部分，让各处保持一致；某一次任务可以完成，整套生活与工作方式仍可继续生长。

## 8. 窃火的三种实践：学习、工作与生活

[窃火与创造能力的培养](https://boluopai.net/philosophy/stealing-fire/)的结论，可以落到三种相互连接的方式：用已有的生成能力帮助理解，让想法成为可用作品，再让日常环境承载它们。目标是兼具人的优势与模型的优势。人的身体经验、兴趣、直觉与整体判断，和模型的检索、比较、显式推理、编辑与执行相互补充；这些是可以调整的贡献，不是把双方锁在固定角色里。听说读写贯穿其中：你听、看、表达、批评和尝试，模型接住这些贡献，整理材料并把下一步工作做出来。

在这套实践中，图对应视觉，语音连接听与说；触觉放在其次，作为辅助。学习时用图示理解概念与关系，再说出疑问；工作时分享草图、截图或流程图，并口述要求和反馈；生活中用照片或简图记录具体情境，说出自己在意的地方。让图与语音成为理解、表达和共同工作的日常方式。

### 多用语音、少用手：把想法说出来，再听回应

与模型讨论时，可以把想到的关系、疑问和例子说出来，听它怎样理解、解释或追问，再补充例子、提出异议、修正原来的表达。让模型承担能够完成的点击、复制、整理、配置和写作，把自己的注意力放在表达、倾听与判断上。这样既减少重复操作，也给听说和推理留下练习机会。

这有点像跟小黄鸭讲解问题：说出来能让尚未成形的想法展开；听自己跟小黄鸭说的东西，能发现表达中需要修订的地方。模型会给出实际回应，可以听或读它的复述，检查它是否抓住真正关心的事。表达、反馈和修订共同推动理解。阅读、书写和实际动手也各有用处，按眼前想理解和练习的能力选择。

语音入口有区别：口述输入法通常把转写文字交给模型，转写可能有误；模型实际收到音频时，声音、语气和节奏才可能进入判断。想练听力时，可以使用实际可用的语音回复或朗读，同时保留文字方便核对。[参与与支持](https://boluopai.net/repositories/prometheus/source/skills/yinyang/references/docs/participation-and-support.zh-CN.html)进一步讨论这些渠道怎样参与理解。

### 学习方式：让模型准备材料，把注意力用在理解

这里培养的是**整体感、直觉与多模态具身推理**：先看见问题的形状和关系，再通过文字、图像、声音、实际操作与反馈，让理解逐步变得可分辨。模型承担细节查找、材料组织和显式推演，让人的注意力留给理解、生成和判断；关键细节在影响结论时仍须展开核对。这样分配注意力，不要求把记住所有细节作为学习的前提，也不把直觉当成无需检验的结论。

可以大范围阅读，并在支撑重要判断的局部深入。只知道某处重要，不一定足以避免误解；必要的基础概念、前提与推理关系，值得通过例子、反例、习题或实验反复练习和评估。模型能给出正确答案，与自己能辨认、运用和修正这个关系，是两种需要区分的结果。局部检验帮助校准整体直觉，不要求把所有知识重新变成全面背诵式考试。

让模型准备相互连接的术语表、主指南和适用的训练材料。数学与技术学习通常采用三份材料，哲学阅读通常采用两份；具体怎样组织、怎样从指南进入原文和练习，集中见[课程与书籍的学习材料](https://boluopai.net/research-learning/#study-materials)。准备时保留较广的知识范围，实际练习时只选眼前实质必要的极少数重点。

**学习材料要让正在读它的人进入问题。**模型既要解释对象是什么、为什么这样理解，也要把它接到你正在看的材料、已经形成的理解、生活经验、兴趣和实际任务上：这个概念回应了你遇到的什么问题，与你原来的想法哪里相合、哪里冲突，理解它之后能重新看见或判断什么。研究只是其中一种关系；即使没有研究计划，也可以围绕一本书、一段经验或一个想做的作品展开学习。

告诉模型正在学什么、已有材料和眼前想弄懂的问题，让它寻找并核对原文，准备容易阅读、能够回查的说明。概念图、文字、声音、实际演示和适用的练习按需要组合；一次孤立问题可以直接解释，持续学习再保留指南、术语与进度。模型写出答案，不等于人已经理解；真正想练习的判断，仍要给自己作出和修正的机会。

保存的材料与当前讲解互相修订。模型根据疑问、异议和反馈调整解释，把有用理解写回材料；原文主张、模型类比与自己的经验保持可区分。记忆、检索、排版和材料维护可以由环境承担，人的注意力留给阅读、辨认、提问、尝试与反馈。普通使用不必先建立一套标准化知识库。

[科研与学习](https://boluopai.net/research-learning/)按目的区分三个入口。想自己给自己上大学、系统补基础与实践知识，可以从兴趣草拟课程，准备材料和环境后写出理论与实践路径；想围绕论文进入陌生领域，可以沿参考文献补基础，再比较相邻问题与方法；日常学习则可以着重理解重要抽象与结论。专页介绍[两个老师](https://boluopai.net/research-learning/#learning)，并说明什么时候需要深入论证、练习和科研检验。学习可以独立于科研，通用工具指南在这里保留入口。

### 工作方式：表达目的，让模型把事情做成

从实际目的或一处不合开始，不必先写完整需求文档。把相关文件或现象交给本地 Codex，让它调查当前状态、比较已有实现、提出有根据的选择，再完成编写、配置、执行与验证。你通过可见的原型、差异和结果判断方向，模型处理它能够调查的细节，把有实质影响的选择解释清楚。

例如做一份报告，模型负责找资料、核对、组织论证和排版；你判断它是否说清了真正关心的问题。修一个工具，模型读取错误、定位并修复，再从原来的入口验证；你检查使用是否顺手。一次完成后，保留源文件、必要说明和版本，让下一次从现有成果继续。反复用到的方法再成为 Skill、脚本或 Hook，避免每个任务都新造一套系统。

### 生活方式：日常事务尽量异步，与模型保持接续

这里还有一种发展节奏的选择。社会制度、软件与交往惯例往往要兼容已有记录、
约定和参与者；自己的知识环境则可以与模型一起面向新能力持续改进。
不必让每一步内部探索都等外部安排同步改变：先把需要展开、把作品做成，
再通过记录、成果和合适的时机与其他关系连接。模型承接这种连接中的细节，
你通过目的、使用和反馈参与。与模型同步，指共同理解和修订能够接续；
与世界异步，指连接可以容许时间差。具体责任、身体需要与现实后果仍决定
哪些事情需要及时回应。[窃火与创造能力的培养](https://boluopai.net/philosophy/stealing-fire/#一种生活方式选择火的节奏)展开了这种向前演进与历史兼容之间的关系。

不让每一条消息、一次更新或一项杂务都要求自己立即切换。适合稍后处理的资料收集、软件维护和提醒，交给已经验证的后台任务，结果在合适时间返回；需要即时回应的人与事，仍按其实际关系安排。异步使不同生活保有自己的节奏，减少被无关进度持续牵动。

与模型“同步”，主要是让正在理解和创造的事情能够连续：同一问题有背景可读，同一作品有源可改，一次反馈能进入下一次行动。它可以发生在短暂交谈、并排阅读或一次作品修订里，不要求全天在线。让环境承接记忆与杂务，把释放出的注意力用于读书、创造、身体活动，以及值得维系的人际关系。日常与模型之间的松紧，随着真实生活继续调整。

### 哲学、心理、工程，一起塑造个人环境

这里最主要的是 **Yinyang 所组织的人与模型的关系**：人可以像语言模型那样生成未完成的想法，模型则像逻辑学家那样展开含义、检查前提并做出成果；关键细节又能使人接过审查，让模型重新生成整体。双方经由对方的贡献返回，保留两种参与的可能。[角色返回的辩证含义](https://boluopai.net/philosophy/yinyang-and-taiji/#经由他者而返回角色变化的辩证含义)说明，这不只是轮流提出和修改方案，也关乎「我能怎样参与」的理解与实际可能怎样改变。

哲学、心理与工程给这条关系带来不同贡献。哲学帮助判断为什么这样生活、怎样理解自己与伙伴；心理方面的理解关注具体经验、感受、欲望、习惯和关系，使安排贴合实际的这个人；工程则把所需的支持做成可用条件。三者可以在同一件事里相互修订。[三位一体](https://boluopai.net/philosophy/local-source-and-website/#世界观认识与实现)展开这份关系，而它在日常中取得形式，要靠**写作、伙伴关系与环境**接在一起。前一组说明各自带来什么贡献，后一组说明这些贡献如何在日常中被表达、相互回应并实现；三种贡献都会贯穿写作、伙伴关系与环境。

**写作，让理解能够被再次使用和改变。**你可以先说出一个想法、偏好、疑问或不满意之处；模型整理材料，比较解释，把有用的理解写成可继续修改的文字。哲学文章可以展开理由和意象，工作描述则说清本人怎样参与、伙伴应该贡献什么、双方怎样合作，以及什么条件支持这项安排。完整采用 Yinyang 时，六份实际描述共同承载这些内容：取向、人、伙伴、关系、环境与修订。相关个人材料与来源保留在私人位置，为描述提供根据。写作本身也能发展理解，不要求你先完成一套哲学，再亲手维护全部文件。

**伙伴关系，让一方的贡献成为另一方继续参与的条件。**你不只提供需求和验收，也能用未完成的表达提出原先没有的联系；模型不只回应或评论，也要发展论证、提出替代、写作和实现。比如你直觉地说「接受帮助可能让我不独立」，模型展开其中的几种理解并写成段落；你发现它把接受支持与失去判断混为一谈，便接过这个细节的审查，模型再按新的区分重写整体。经过这次返回，你仍可以开放地生成，也能够接过关键判断；模型的再次生成则带着审查显出的条件。实际效果要看使用与后续参与，不能仅凭写好一段描述就认定能力已经发展。

**环境，让这种往返能够实际发生。**模型要能找到有关材料、读到当前描述、使用需要的工具，并把作品放到你能看到、试用和修改的位置。你指出一处不合，它应能返回对应的原文、配置或作品，把改变落实并验证。文件、记忆、提示词、Skills、应用与自动化因此各有用途：保留什么，怎样接续，能做什么，结果怎样回到生活。环境也把共同创造带到会独立回应的现实中，使使用的不便、来源的反驳或作品的后果能够改变原来的安排。

把这三项连起来，一次口头生成就不必停在聊天里：模型可以写出理解，与你继续判断，再修改阅读入口、学习材料、工作工具或日常安排。你学习的是怎样参与、怎样判断关系是否合适、哪些复杂性值得保留；模型承担它能完成的调查、配置、代码、调试和检查。工具更多、文件更齐全，并不自动使这段关系更好；实际能否理解、生成、纠正和完成工作，才给调整提供根据。

这些实践可以从眼前需要开始。想进一步写出自己的安排，可沿[哲学与模型](../design-and-revision.zh-CN.md)进入六份写作指引；想了解三种贡献的根据，可按问题选择[哲学阅读](https://boluopai.net/repositories/prometheus/source/skills/yinyang/references/docs/philosophical-readings.zh-CN.html)、[心理阅读](https://boluopai.net/repositories/prometheus/source/skills/yinyang/references/docs/psychological-readings.zh-CN.html)与[工程阅读](https://boluopai.net/repositories/prometheus/source/skills/yinyang/references/docs/engineering-readings.zh-CN.html)。借用其中一种方法，也可以直接服务于当前任务。

## 9. 让模型持续监督、收集与修复

环境建成以后，把需要反复关注的工作交给模型与自动化。个人只需表达正在关心什么、哪些结果有价值，模型把这些需要落实成可运行的定期任务、变化检查和故障处理。目标是覆盖个人实际需要的各类资料与维护工作，减少反复检索、切换软件、对照版本、下载整理和排障。

### 网页追踪变化，本地加工材料

**网页可以直接收集的信息单元：**一个工具的发布说明、一项订阅的价格与额度、一篇新论文的题录与摘要、一场会议的议程、一个活动的报名时间。模型定期检查这些对象的页面与一手来源，保存链接、日期、必要摘录和相对上次的变化，形成可以浏览和判断的信息流。这类任务通常不需要先把整套资料下载、转换一遍。

**需要额外处理、供自己实际使用的材料：**论文和教材全文、扫描 PDF、成套课程、视频讲话文本、个人笔记，以及实验代码与数据。模型取得需要的版本后，在本地完成核验、OCR、转换、翻译、分组、索引和链接，或准备运行环境，再放进适合阅读与维护的文件夹、Obsidian 库或项目。完成标准是材料确实可读、可查、可运行或可接续，而不只是搜到一个网页。

两类工作通过原始链接、版本与处理记录连接。先从变化信息判断相关性，再把值得使用的对象送入本地加工；已有材料更新时，只处理实际受影响的部分。这里的网页采集通常也由本地任务调用搜索和读取工具完成，不要求另外打开 Web ChatGPT 对话。让采集保持轻量，让真正使用的材料获得足够整理。

### 按实际需要安排长期工作

**Web 定时任务与本地定时任务，先区分执行位置。**在 Web ChatGPT 中，可以用 **Scheduled Tasks（定时任务，创建按钮为 Schedule task）**安排每周跟进资料、检查变化或接续进度，并在 Scheduled 中查看结果、修改安排或暂停。Web 任务不会直接获得本地文件夹的访问能力。给任务写清长期目的、本次工作与结果位置，让模型核对这项任务实际可用的来源和工具，并检查真实产出；可参考[定时任务说明](https://help.openai.com/en/articles/10291617-scheduled-tasks-in-chatgpt)。

**本地定时任务在接通的电脑环境中执行。**例如，桌面客户端的[本地自动化](https://learn.chatgpt.com/docs/automations?surface=app)可以围绕项目或 worktree 安排工作，使用实际可访问的目录、Skills 和工具；需要电脑开机、应用保持运行。让模型核对执行位置、访问范围、触发时间和输出，再试跑一次。保存了时间表或显示“已启用”，还要有实际执行和结果可查。

**Dot 可以组织持续工作，并在实际接通的现场执行。**沿[三种工作现场](#continuity)的区别，选择它自己的云端电脑、已配置的仓库环境，或另行接通的本地任务；管理入口以[当前官方说明](https://learn.chatgpt.com/docs/dots/computers-and-apps)与账号为准。简单、大量、重复的环节可以逐批交给它：准备术语表、文字解释和学习指南，批量翻译工程文档、注释与说明，或承接复杂项目中能独立交付的翻译工作。让结果回到原有文档、仓库或项目维护位置，随后核对内容与进度，不另留一份失去联系的云端副本。

交代原文、目标语言或材料形式、术语约定、已完成范围和输出位置，让它分批保存结果、记录进度，并接着处理下一批。学习材料还要说明“这些概念与我正在理解的问题有什么关系”，使材料保有前面说的读者联系；工程翻译则保留文件与段落对应，并把结果交回项目核对。用反馈改进后续批次，遇到需要整体判断或复杂环境操作的部分，再交给负责整个项目的模型接续。

定时任务规定何时启动，选定的工作现场决定可用材料与工具，Dot 等入口可以组织和接续工作；它们是能够配合的不同安排。涉及本地文件、软件配置或设备时，核对实际接通的本地能力。无论选哪一种，都检查真实来源和产出，准备完成也不等于读者已经理解。

### macOS：LaunchAgent 触发工作，监测验证结果

在 Mac 上，还可以让模型把适合的脚本或服务接到 **LaunchAgent**，由系统的 launchd 按需、定时或持续运行。LaunchAgent 属于已登录用户的会话；关机时不会执行，睡眠和唤醒也会影响触发时间。配置时对照当前 macOS 的本机手册与实际测试；[Apple 的 launchd 说明](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html)是基础参考，但属于归档文档。

把它接到已有的轻量监测中，让模型通过 launchctl 状态、日志和实际产出检查运行。常驻服务看进程健康与功能；一次性任务看最近成功时间、结果是否按期更新和错误记录，空闲时没有进程可以是正常状态。监测发现异常后，由模型读日志、诊断并在已授权范围内修复或恢复，再从原任务入口验证；需要重试时限制次数，避免反复启动或重复通知。对有意义的失败、恢复或需要人选择的情况发出可行动的提醒，未变化的例行检查保持安静。

### 用个人服务器接续本地工作

也可以把 Mac mini 一类电脑作为**个人服务器**，承接需要本地文件、应用或设备的长期任务，按需要提供 24 小时持续运行的环境。模型可以在其上定时收集资料、准备学习材料、检查服务和维护环境；你的日常电脑不必一直承担这些后台工作。是否另设机器，取决于已有设备和实际任务，不是开始这套方式的前提。

持续运行要落实到电源、网络、机器保持可工作状态、任务调度，以及重启后的恢复。让模型配置并验证一次“触发任务 → 执行 → 保存结果 → 中断后接续”的实际路径；模型服务或网络暂时不可用时，记录失败并在合适时重试。这里的 24 小时说的是运行安排，不是每项服务永不故障的保证。个人服务器负责提供环境，本地定时任务或 LaunchAgent 等负责何时启动，模型与工具负责具体执行，监测则检查工作是否真的完成。

- **新插件与新工具：**持续留意官方发布、GitHub 项目和社区使用经验，判断新能力能否替代复杂操作、简化现有工具或打开新的工作方式。找到合适实现后，按“采用、配置更新、适配，缺少时再编写”的顺序接入环境。
- **模型与软件版本：**检查真实可用的模型、客户端、插件和软件版本，结合它们当前承担的工作判断是否升级。完成更新后验证实际入口，把必要配置改动回收到 chezmoi 与对应项目；版本号变新本身不是工作完成。
- **订阅价值：**先检查主订阅的稳定性、账号与续费可靠性，再把本地加 Web 的实际能力和用量放在一起，参考可比模型的当前 API 价格评估使用价值。优先个人 ToC 方案，不为短期优惠频繁换订阅；确有能力、可靠性或组织需求变化时，再提出保留、升级、降级或更换的建议，并在已有授权范围内处理后续操作。
- **论文、基础资料、会议与实验材料：**按正在学习和研究的问题，定期寻找论文原文、作者资料、课程教材、官方会议议程与征稿、演讲材料，以及实验的代码、数据、方案和复现说明。保存原始来源、版本与日期，去重并连接已有材料，区分收集到的说明与已经实际验证的结果。
- **关注的活动：**从主办方公告、官方日历和报名页面取得一手信息，记录时间、时区、地点、报名条件与截止日期，继续跟踪变更。把对个人有用的变化带回来，减少不断刷新多个网站的操作。
- **环境自动修复：**监测服务退出、接口失效、同步异常和更新后的功能回退。让模型读取实际状态与日志，定位原因，完成范围内的修复，把必要修改保存到配置源，并通过原来的使用入口验证恢复；无法自行完成的具体问题再带给人判断。

可以让模型建立这些自动化：软件与模型变化检查、工具生态评估、论文雷达采集与评估、Skills 更新、Web 能力同步，以及服务故障后的模型修复。读者可以把同样的组织方式扩展到自己的资料、会议、实验与活动。这里介绍的是工作方式；写下一段“自动关注”的提示词，还不等于已经建立了能持续执行的任务。

请模型把每项长期工作接到实际调度或事件触发上，确定资料来源、执行频率、存放位置、可自行处理的动作与需要人判断的情况，并验证一次真实运行。保留上次进度、已处理记录与失败状态，避免每次重新收集或重复通知。结果更新到人能找到的资料与界面中；重要发现、完成、失败或需要选择时再提醒，未变化的日常维护保持安静。模型也继续检查这些自动化自身是否还在工作，让复杂操作留在环境里，让人的注意力回到理解、选择和创造。
